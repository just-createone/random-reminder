- FastAPI 路由、鉴权、会话与用户数据隔离；
- 提醒、设置、每日计划、通知历史与 Web Push；

## 3. 主要发现

### A-01：公开登录与注册接口缺少请求限速

级别：P1（公开测试前）

`/api/auth/login` 和 `/api/auth/register` 没有按来源、账号或失败次数实施限速。密码哈希本身安全，但公开部署仍可能遭遇撞库、枚举式注册和资源消耗攻击。

建议：在可信反向代理层增加基础限速，同时在应用层增加登录失败节流和可观测指标。代理层必须基于可信代理链解析客户端地址，不能直接信任任意 `X-Forwarded-For`。

### A-02：服务端通知可能被标记为“已发送”但未真正触达用户

级别：P1

执行器优先发送用户专属 Web Push；没有有效订阅或推送不可用时，会退回服务器本机通知或控制台输出，随后仍把通知和计划标记为 `sent`。在 Linux 公开部署中，控制台输出并不等价于用户触达，因此历史状态可能过度乐观。

建议：把“已投递到用户渠道”和“仅记录到服务器日志”拆开；没有用户渠道时应保留可重试状态或记录明确的 `undeliverable` 状态。

### A-03：多进程/多副本执行器存在重复投递窗口

级别：P1（扩容前）

执行器在 FastAPI lifespan 中启动线程，发送成功后才更新数据库状态。当前单进程部署模型下可以工作；如果以后启用多个 Uvicorn worker 或多个应用副本，两个执行器可能同时读取同一条 pending 任务并重复发送。

建议：公开部署保持单执行器；扩容前引入带租约的原子 claim，或把调度执行器拆成唯一 worker。不要只依靠发送后的状态更新解决竞争。

### A-04：浏览器 Web Push 不能直接作为 Flutter 原生通知通道

级别：P1（移动端设计约束）

现有 `/api/push/subscriptions` 接受浏览器 Push API 的 endpoint、p256dh 和 auth；Flutter Android 原生应用不能把 FCM token 当作该结构提交。

MVP 决策：Flutter 复用账号、提醒、设置和今日计划 API，在设备端把服务端计划排程为本地通知。后续若需要跨设备、长期后台和无需打开 App 的可靠触达，再新增独立的设备注册模型并接入 FCM/APNs，不能复用 Web Push 表伪装实现。

### A-05：设置和提醒变更不会自动重排当天已有计划

级别：P2

更新总开关、时间范围、次数、间隔或提醒启用状态后，已有的当天计划保持不变，除非用户显式强制重新生成。这个行为在数据层一致，但用户可能误以为保存设置立即生效。

建议：Web 与 Flutter 均明确提示“设置影响下次生成”；提供显式“重新生成今日计划”操作，避免保存设置时静默删除现有计划。

### A-06：注册用户与初始化用户设置不是同一事务

级别：P2

用户记录创建提交后，才执行设置初始化和旧单用户数据认领。后一步异常会留下无法正常读取设置的半初始化账号。

建议：将用户创建、默认设置和一次性旧数据认领放入同一数据库事务，或实现可重复执行的登录时修复。

### A-07：通知历史的“今天”默认使用服务器本地日期

级别：P2（多时区）

计划生成与执行按用户 IANA 时区处理，但通知历史 Repository 在调用方未传日期时使用服务器 `date.today()`。服务器日期与用户当地日期不一致时，pending 历史可能显示错误。

建议：API 从当前用户时区计算当地日期并显式传入 Service/Repository。

### A-08：部分所有权列缺少数据库外键约束

级别：P2

`reminders.user_id` 与 `push_subscriptions.user_id` 依靠应用查询隔离，但数据库 schema 没有对 `users.id` 建立外键。删除用户或迁移异常时可能留下孤儿数据。

建议：通过可回滚的 SQLite 表重建迁移补齐外键和 `ON DELETE CASCADE`，迁移前先检测孤儿记录。

### A-09：前端统一错误处理假设响应始终为 JSON

级别：P3

反向代理 HTML 错误页、空响应或网络中断会让 `response.json()` 抛出二次错误，丢失状态码和更有用的上下文。

建议：按 Content-Type 和响应体是否为空解析错误，并保留 HTTP 状态码。Flutter API 客户端按此原则实现。

### A-10：本地工具链不可复现

级别：P2（开发体验）

仓库内 Python 虚拟环境记录了错误编码后的中文路径，无法直接启动；系统 Python 加载该环境的 site-packages 后可以完成测试。Flutter、Dart、JDK 和完整 Android SDK 在审计开始时未加入 PATH 或未安装。

建议：不要提交或复制虚拟环境；记录可复现的 Python 与 Flutter 版本，并在无特殊字符的工具目录安装 SDK。CI 应独立执行 Flutter analyze/test/build。

## 4. Flutter Android MVP 范围

MVP 必须形成以下闭环：

1. 使用线上或可配置的 HTTPS API 地址；
2. 注册、登录、恢复会话和退出登录；
3. 查看、新建、编辑、启停和删除提醒；
4. 查看和保存随机提醒设置；
5. 查看、首次生成和显式重新生成今日计划；
6. 用户主动授权后，将未来的 pending 计划排程为 Android 本地通知；
7. 会话令牌存入平台安全存储，日志和错误中不输出令牌；
8. API、模型和通知服务保持平台无关，便于后续复用到 iOS。

MVP 明确不包含：

- 修改现有 Web/PWA 推送协议；
- Firebase/APNs 服务端推送；
- 微信小程序；
- 后台静默跨日生成计划；
- 自动部署、提交、推送或线上环境修改。
